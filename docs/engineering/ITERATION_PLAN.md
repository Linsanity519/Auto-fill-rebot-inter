## 1. 建议确认的总体方向

把现有助手逐步改造成一个**个人可维护、按需运行的本地配置应用**：保留熟悉的桌面界面和全部现有业务能力，抽出共用的领域规则与任务编排，使用本机 SQLite 保存完整任务档案，通过本地 MCP 让 AI 调用这些能力。多人各自在自己的电脑执行，优先扩展现有智能表格回传和收集端，让维护者继续在已有入口查看汇总与新增明细。

当前不需要租服务器、买域名、安装数据库服务器，也不需要把电脑 24 小时开着。执行任务或等待定时任务时，需要电脑开机且不休眠、内网连接与所需登录态有效。全天候远程执行、实时集中调度属于未来扩展。

你提出的“领域规则—编排流程—前端调用—数据库操作”是可行方向。建议补充两点：**业务核心不依赖具体数据库或浏览器；GUI、CLI、MCP 共同调用同一组业务用例。** 这样换界面、接 AI、替换平台接口时，业务规则和执行语义仍能复用。

现有项目已经有架构雏形：配置文件和注册表决定功能，runner 编排，filler 操作页面，还有模板、断点和结果模块。主要问题是职责交叉、状态管理分散、入口行为不一致；应沿业务功能逐项迁移，保留已有的平台经验。

## 2. 目标架构与运行方式

### 2.1 五个代码边界，一个本地应用

```text
桌面界面 / CLI / 本地 MCP
             ↓ 规范化输入、计划与任务查询
       application：业务用例与编排
             ↓               ↓ 通过应用层定义的端口
       domain：领域规则      adapters：具体外部能力
                            ├─ 平台 API
                            ├─ 浏览器会话 API / Playwright
                            ├─ SQLite / 文件附件
                            └─ Excel / 档案归集

bootstrap 负责组装；domain 和 application 不导入具体适配器。
```

| 落点 | 负责什么 | 举例 |
|---|---|---|
| `src/domain/` | 纯业务数据、确定性规则 | 延期是否符合条件、配置输入是否有效 |
| `src/application/` | 用例、任务编排、输入输出契约、外部能力端口 | 生成计划、执行已授权计划、核验结果、恢复任务 |
| `src/adapters/` | 实现外部能力 | 读写平台、操作页面、保存 SQLite、解析 Excel |
| `src/entrypoints/` | 把入口请求转换为用例调用 | 桌面桥接、CLI、MCP 协议 |
| `src/bootstrap.py` | 构建与连接依赖 | 选择平台适配器、仓储和本地任务服务 |

分层内部再按价格、投放、授权、人群、实验、会议组织。共享的是任务机制、数据读取等稳定能力；每个平台的规则和页面差异保留在对应模块。现有平铺模块作为过渡区，迁移完才删除，不额外建立万能 `utils` 或巨型父类。

### 2.2 推荐采用单一本地任务宿主

为避免 GUI 和 MCP 分别启动执行器争抢同一浏览器，最终由助手自己的一个本地进程统一持有任务、写入任务状态并管理 Playwright。GUI、CLI 和 MCP 只传递任务数据。

- 宿主按需启动；M2 实际使用 OS 文件锁与 SQLite 本机持久命令队列，取代原拟命名管道方案，理由和当前用户权限边界见 [ADR-0002](decisions/0002-local-task-runtime.md)。
- MCP 采用本地 stdio 接入宿主；业务接口先是有类型的 Python 用例，无需为“API 化”额外开放 HTTP 服务。
- Playwright 的 Page/Context 由执行线程或事件循环持有，不跨线程交给 GUI/MCP 使用。浏览器会话绑定明确的账号与环境，不盲选第一个标签页。
- 首期对共享浏览器的写任务串行执行。任务可排队，但排队后的状态必须在提交前重新检查。没有证据证明隔离可靠前，不增加并发写入。
- 聊天断开不终止已接收任务；界面展示任务仍在助手中运行。退出助手时明确显示在途任务，停止继续派发并记录中断，不把“已接受”当作“始终在运行”。电脑重启后先核验未知步骤，再决定续跑。
- M1 先补当前程序的互斥和启动防重；M2 再收敛到单一宿主，避免同时改掉所有执行路径。

这里的“宿主”是本机程序，不是需要租赁或运维的服务器。多台电脑各有宿主；档案同步不提供跨电脑锁定。首期通过分配不同账号/对象范围避免同事同时修改同一对象，不能承诺跨设备全局互斥。

### 2.3 浏览器、API 和前端的关系

当前调用链是“助手 HTML/JS → pywebview 的 Python 桥接 → Playwright/CDP → Chrome”。因此，道听途说的“浏览器规则不允许一个浏览器控制另一个 Page”不能用来判断本项目不可行。普通网页的同源边界与本机 Python 使用自动化协议是不同机制。[Playwright 的 CDP 接入文档](https://playwright.dev/python/docs/api/class-browsertype#browser-type-connect-over-cdp)明确提供后一类能力。

为助手选择 TypeScript 组件框架，只影响助手自身界面的组织方式；不会替代内部平台操作，也不是重构前提。本轮保留 pywebview 和现有界面，按功能拆分 `app.js`，验证本地资源加载与打包。

每项平台操作按下面的次序评估，并在执行前选定适配器：

1. 有稳定、可认证、允许使用的平台 API：优先采用，并测试业务结果回读。
2. 接口需要浏览器登录或页面签名：封装浏览器会话 API，浏览器仍承担必要职责。
3. 缺少可靠接口：继续 Playwright，集中管理定位、超时和兼容逻辑。

会议功能当前依赖页面签名，不能提前承诺完全脱离浏览器。接口超时且提交结果未知时，必须先核验；不能立即换 Playwright 再提交一次。无论哪种方式，业务用例看到的是同一标准结果。

## 4. 臃肿与冗余的精简方案

### 4.1 已确认的候选及处理方法

源码基线有 80 个 `src` Python 文件、约 29,520 行；`webapp.py` 1,621 行、`app.js` 4,753 行。文件长度只用于定位混合职责。AST 扫描发现 12 组函数体结构相同的候选，尚不能据此直接删除；参数默认值、调用环境、异常语义仍须核对。

| 部分 | 源码证据 | 精简方式与边界 |
|---|---|---|
| 重复 Excel/CSV 读取 | `ab_data.py:40`、`dmp_data.py:40`、`hh_data.py:49` 的 `_read_rows` 相同 | 提取表格读取适配器；保留各领域的字段解释和校验。覆盖空行、表头、行号、公式读取等行为 |
| 两套商广读取逻辑 | `ad_data.py:110`、`adv2_data.py:71` 的 `_rows` 相同，隐藏列处理也重复 | 共享读取与值规范化，保留隐藏行列过滤、长整数和单元格格式语义；不与普通读取器强行合成一种默认策略 |
| 重复结果 CSV 导出 | `ad_reg_runner.py:387`、`ad_runner.py:414`、`adv2_runner.py:276` | 统一导出适配器；任务数据库是执行事实来源，CSV 是派生文件，导出失败可重试且不能伪装成功 |
| 重复等待与页面控件 | `pp_filler.py:108`、`wizard_filler.py:53` 等 | 优先复用已有 `fill_core` 能力；统一条件等待和期限，保留平台定位差异，不照搬吞异常逻辑 |
| GUI 桥接类承担过多职责 | `webapp.py` 的 Api 类有 65 个方法 | 把规则、任务生命周期、归档、更新逻辑移出入口；桥接只做输入输出与界面事件 |
| 前端大文件 | `assets/webui/app.js` | 按表单、计划、任务、历史、设置拆分；逐页验证 pywebview 的文件加载、交互和安装包资源 |
| 多套 runner 中的相似流程 | AB/DMP、各商广 runner | 共享任务调度、状态、错误和结果机制；AB/DMP 的平台规则、DOM 和不同商广步骤仍分别实现 |
| 台账、状态、清单与历史文件 | `runstate`、`manifest`、价格/资源位 ledger 等 | 新任务以 SQLite 中的结构化记录为准，旧数据通过迁移器导入；不永久双写两套互相冲突的执行状态 |
| 历史兼容与统计通道 | 旧模块、配置回退、`usage.py` | 查清仍在使用的版本和入口后逐项弃用；离线发件箱/重试等可复用，不因分支多就判为无用 |
| 文档、脚手架和依赖 | 旧项目地图、`tools/new_mode.py`、宽泛依赖下限 | 规范入口统一；脚手架改为生成分层结构；锁定经验证依赖，删除依赖前确认动态加载与打包需求 |

候选函数已人工抽查，证据见[精简候选记录](BASELINE.md)。代码共享必须基于相同语义；几个相似构造函数不足以成为引入复杂继承的理由。

### 4.2 删除旧代码前的四个条件

1. 对应功能、字段、模式和兼容分支已登记，代表性输入与结果有对照样例。
2. 检查静态引用、动态注册表、配置文件、录制流程和打包/更新清单，确认没有遗漏调用入口。
3. 新实现通过相关离线回归及必要的平台验收，包含失败、部分完成和恢复路径。
4. 新版本默认使用新实现，旧用户数据有迁移与回退办法，再删除旧实现并收窄架构存量清单。

迁移期间允许有明确退出条件的临时旧适配器；不永久维护两套等价业务引擎。按模块记录删除了什么、哪些重复点消失、留下什么兼容原因。**不设置“代码必须减少 30%”之类指标**：增加状态、恢复和验证机制可能短期增加代码，目标是减少重复职责和维护成本。

## 5. 数据库位置、多人归集与历史数据

### 5.1 数据落点

下面是拟议默认路径，当前旧版仍主要在程序旁使用 JSON/JSONL/CSV 等文件：

```text
%LOCALAPPDATA%/ConfigAssistant/
  data/tasks.sqlite3          本人的任务与事件
  attachments/<task_id>/      原始输入、截图、结果文件等
  exports/                    用户导出的完整档案包
  backups/                    数据迁移与升级备份
  collection/archive.sqlite3  维护者可选的本地缓存/离线分析库
  collection/attachments/    下载或导入的档案附件（按需）
```

提供“打开数据目录”“导出档案”“备份/恢复”等界面入口，使用者不需要手动编辑数据库。SQLite 是本机文件；多人各自使用各自的库，不能把同一个正在写入的库放到网盘上让大家共同写。[SQLite 官方使用建议](https://www.sqlite.org/whentouse.html)说明了本地数据场景和网络文件访问的限制。

### 5.2 完整档案包含什么

| 数据 | 保存内容 |
|---|---|
| 配置 | 原始输入文件、规范化完整配置、模板/表单/流程/规则版本或必要快照 |
| 计划 | 目标账号与环境、稳定对象 ID、变更前后、范围、跳过原因、计划有效条件 |
| 授权 | 计划版本、授权来源、时间和适用范围；用户身份无法验证时明确标为声明 |
| 操作 | task/item/step/event ID、入口、设备、实际平台身份、步骤时间和状态 |
| 结果 | 逐项成功/失败/跳过/未知、平台对象、回读证据、错误与恢复建议 |
| 附件 | 输入、输出、必要截图等包内引用及校验值；缺失明确标记 |

Cookie、密码、会话令牌不属于业务配置档案。历史文件缺少的账号、前值或证据标为“旧版未记录”，不能事后编造。新能力启用后生成完整档案；这不能保证旧数据也能补成同样完整。

### 5.3 优先扩展现有回传结构

v1.1.24 已有主链路：**本机运行记录 → 持久化发件箱 → 智能表格“接收外部数据” → 收集端查询/去重 → 团队统计。** 企微群机器人是另一条备用通道。这套结构已经利用现有平台接收数据，不要求维护者自己的电脑持续在线。收集和刷新汇总时，维护者电脑需要运行相应工具。

此前将手动档案导入设为默认，是把“现有内容不完整”扩大成了“需要另一条归集路线”。修订后优先复用已有传输、接收和查看入口；完整档案包保留为断网补交、迁移和备份能力。

| 现有实现 | 可复用部分 | 完整档案所需补充 |
|---|---|---|
| `usage.py` 的运行事件 | 稳定关联一次运行、已有埋点调用位置 | 当前主要是统计；新执行库需持久保存完整配置、步骤和证据，不能从成功数量反推 |
| `report.py:282` 的 `run_payload` | 显式字段契约与版本 | 现有白名单是运行摘要；完整业务档案使用独立版本化数据模型，不混入公共统计 |
| `report.py:332` 的发件箱及 `push` | 先存后发、失败补传、通道分别记账 | 完整档案需要可靠持久化、逐记录状态和可核验接收结果，不能吞掉数据保存失败 |
| `report.py:531` 的表格映射 | 向既有智能表格投递的适配方式 | 新字段/明细表映射、正文或分片、版本、任务/条目/事件 ID、缺片检查 |
| `collect_usage.py:595` 的表格查询 | 现有收集端权限与按运行 ID 去重 | 分页/增量拉取、明细检索、内容冲突和完整性检查；完整记录不压缩成团队总数 |
| `team.json` 与原表格看板 | 现有团队统计体验 | 继续只派生允许公开的统计；完整配置在访问范围合适的业务明细表查看 |

**建议实施结构：** 本地完整档案 → 持久化发送队列 → 现有智能表格中的任务/条目/事件明细 → 现有收集端核验与汇总。优先新增明细子表，保留原统计表兼容；若现有表共享范围不适合业务详情，则在同一现有平台新建权限合适的明细表，不因此引入自建服务器。维护者本地库仅用于缓存、离线分析或备份，不是必装的第二套管理中心。

实施前需要验证现有平台和实际授权的几个具体能力：字段/请求体容量、行数及速率、可查询性、附件上传与下载、接收结果、明细表访问范围。当前源码能证明摘要回传已实现，不能单独证明现有入口能接收任意大小的文件或全部业务字段。

- 完整配置、变更前后和步骤结果优先以结构化明细或带版本的 JSON 保存；超过实际字段限制时再按验证过的规则拆分，禁止静默截断。
- 截图、Excel 等附件优先使用现有平台可用的附件能力并关联任务。现有 webhook 实现只有记录写入，尚未发现完整档案附件通道；若确实不支持，再选择已有且适用的文件位置，手动补交是最后回退。附件只存本机路径不能算已回收。
- 用户执行后自动投递，离线时保留队列，后续启动补传。远端明细收齐后才能标为“已完整归集”；接口接受、读回核验、附件齐全分别记录。
- 当前 `_send_sheet_batch` 对部分拒收行会结束表格重试，这种统计降级语义不能用于完整档案。应保留拒收原因和待处理状态；群消息通知不能代替完整内容已被接收。
- 同一记录重复到达不重复计算；同一 ID 内容不同显示冲突。收集端不能仅在触及查询上限时提示一下就将已读取部分当成全量。
- 企微群继续承载统计、提醒和现有摘要回退，不默认发送完整业务详情。完整配置不进入公开 `team.json` 或公共发布仓库；收集端已有的广泛读取/管理凭据不下发客户端。

导出/导入包仍需版本化 manifest、内容和附件校验、重复/冲突处理、接收回执及导入失败恢复。它与自动通道使用同一档案契约，避免维护两套数据结构。

默认不自动删除业务档案；界面显示占用，允许先备份再清理。本地执行记录与远端完整性分别核验；收集到历史不等于取得另一台电脑的执行控制权。

## 6. MCP/API 后，如何让人和 AI 理解操作

### 6.1 保留可见界面，统一底层说明

建立版本化“能力定义”：功能用途、前置条件、字段类型、必填、单位、合法范围、示例、条件依赖、动态选项查询、副作用与结果。桌面表单、模板说明、MCP 输入 schema 和结果摘要从同一份业务定义派生；具体布局仍可独立设计。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)提供输入/输出 schema 与结构化结果，本项目还需在程序中实际执行校验。

| 用户需要知道什么 | 桌面呈现 | MCP/API 呈现 |
|---|---|---|
| 能做什么、要什么信息 | 功能说明与表单 | 能力说明、字段 schema、真实选项查询 |
| 还缺什么 | 定位到具体字段 | `missing_fields`、合法值、针对性补充说明 |
| 会改哪些内容 | 账号/环境、对象、前后差异和跳过原因 | 相同的存档计划及中文摘要 |
| 是否已经获得授权 | 对具体计划确认，或显示有效的既有授权 | 校验计划绑定的授权记录；模型自述不能代替授权 |
| 现在到哪一步 | 任务进度与逐项状态 | `job_id`、状态/事件查询、结构化错误 |
| 到底成功了吗 | 已核验结果、失败/未知和证据 | 同一结果对象、证据引用、下一步 |

不能承诺 schema 或 Skill 让每个模型永远理解正确。程序必须做到：缺关键字段不提交、账号与范围不猜、参数变化使旧计划失效、状态不明不假报成功。用固定案例验证常见 AI 调用是否遵循这些边界。

### 6.2 一次操作的完整流程

以“关闭一批价格策略”为说明示例，示例数字不代表实际业务数据：

1. AI 查询能力和真实可选项；缺账号、范围或目标状态时询问这些字段。
2. 助手校验输入并只读预检，生成存档计划：“账号 A / 环境 B；拟关闭 8 项；2 项已关闭将跳过；1 项无法核验，暂不执行”。
3. 用户在本地计划页看逐项变化；如已有可验证且覆盖该计划范围的授权，直接复用，无需重复确认。否则确认这份具体计划。
4. MCP 提交 `plan_id`，宿主验证计划版本、授权、账号与最新前置状态后执行；不能用相同 ID 偷换入参。
5. 返回逐项核验结果，例如“7 项已关闭，1 项待核查”，同时展示完整档案的位置与归集状态。

普通 MCP 客户端使用文字和结构化结果，本地桌面计划页始终可用。MCP Apps 可在支持的宿主内增加交互表单，但不作为所有宿主的必需条件。[MCP Apps 官方说明](https://modelcontextprotocol.io/extensions/apps/overview)

### 6.3 接入范围

- 工具按用途暴露：查询能力/选项、校验与准备计划、查看计划、执行已授权计划、查任务/结果、取消后续步骤、核验未知结果。已有稳定业务用例才开放对应写工具。
- 每项已迁移功能提供清楚的工具 schema；共享任务查询与控制工具，避免把所有功能塞进无约束的 `execute(action, dict)`。
- 配套 Skill 教 AI 何时补参、如何解释计划、如何区分“请求发出”和“生效”、遇到未知结果如何处理。Skill 不保存另一套业务规则，不提供任意脚本执行捷径。
- 取消只停止可停止的后续操作；不会自动撤销已经成功的配置。反向变更需要自己的计划和核验。
- 云端模型可能接收用户输入和工具返回内容，因此默认返回完成当前任务所需的信息；完整档案在本地保存并按 M3 归集，AI 按需查询，不自动接收全量归集内容。不能把“本地执行”解释成“模型通信也完全在本地”。

下表沿用原评审编号，表示源码基线的发现；除规范门禁外，不能把建议当成已经修复。详细复现和源码位置见[架构评审](BASELINE.md)。

| 编号 | 问题与证据状态 | 处理与验收 | 阶段 |
|---|---|---|---|
| F01 | 筛选后行下标变化导致续跑漏项，已复现 | 稳定 item ID 全链路透传；筛选、无效行、部分重试都不漏做或错记 | M1 |
| F02 | 断点写盘失败仍继续，账号/范围隔离不足；写盘问题已复现 | 关键写入失败阻止新提交；外部提交后落盘失败进入待核查；M2 使用事务仓储 | M1、M2 |

| F07 | 普通授权没有使用返回的历史申请次数；本地处理缺口已复现 | 核实字段与配额时间窗口后制定规则，配额未知时不自动执行；不能先编造计算公式 | M1 核实；M5 完成 |
| F08 | 反向操作忽略传入 run_id、按名称定位，源码确认 | 绑定指定任务、账号、父对象和平台 ID；比较 before/after/current；不可核验则解释原因 | M1、M2、M5 |

| F10 | 原版本缺统一质量门禁 | 本地规范、检查、构建和发版门禁已准备；远端 CI、必需状态检查待启用，依赖锁定待完成 | M0、M6 |
| F11 | 更新备份在新版本健康启动前被清理，源码确认 | 健康启动确认后处理旧备份；验证代码/运行时/数据迁移失败的恢复 | M6 |

外部平台提交和本地数据库不可能自然组成一个事务。平台不提供幂等机制时，本方案不承诺数学意义的“只执行一次”；通过稳定标识、提交前记录、回读、互斥和未知状态处理避免盲目重复。MCP 写入开放前，必须先通过该功能相关的正确性验收；其他尚未迁移功能继续使用既有入口并明确限制。

## 8. 分阶段迭代与可交付成果

### M0：固定基线，补齐验收，确认工程规范

**交付：** 全功能行为矩阵、代表性脱敏样例、已知缺陷清单、迁移清单、现有质量门禁的可复现记录。

- 保留 v1.1.24 源码与可用安装包基线；当前治理改动单独记录，避免把它们当成原始版本。
- 按第 3 节盘点字段、模板、模式、输入输出、动态注册和流程配置。已有测试不足处，只补能验证真实行为的用例。
- 记录启动、表格读取、计划生成、打包体积等可在本地测量的基线；内网执行时间在有真实环境时再测。
- 把既有复现转为持续回归，登记四项环境测试的运行条件。历史样例由已有脱敏材料开始，缺少材料的功能明确列出待验证项。
- 检查规范和脚手架入口；在后续新增功能前改造旧 `new_mode.py`。

**通过条件：** 每项现有功能都能对应到行为清单和验证方式；离线检查通过；没有用“目前没有测试”解释为“功能可以删掉”。

### M1：优先修复状态与执行正确性

**交付：** 范围受控的稳定性修复、每项问题的复现/修复对照、必要的界面文案修正。

- 优先修复 F01/F02/F04/F06，补稳定标识、关键存储失败处理与启动防重。
- 修正 F03/F08/F09，明确只读/真实写入、精确反向操作和未知预检结果。
- 为提交超时和部分成功加停止盲目重试的边界；逐项列出尚缺核验能力的旧功能。
- F07 先核实平台含义，不能仅靠字段名决定规则；核实前保持“资格未知”的可见状态。
- 只提取修复直接涉及的公共逻辑，不同时大改界面和全部 runner。

**通过条件：** 原复现用例不再出现漏项、虚假持久化或重复启动；相关入口语义一致；只读模式没有业务写入；未知结果不会自动再次提交。平台事实尚未确认的项保持未完成，不计为通过。

### M2：搭建共用内核，以价格策略批量开关贯通

**交付：** 新分层、本地任务宿主、SQLite 首版、变更计划、任务中心、价格策略开关的 GUI/CLI 新路径。

- 实现领域规则、应用用例、平台端口与存储端口，把旧页面适配暂时接在 `adapters/legacy`。
- 任务库记录输入、计划、授权、对象、步骤和事件；实现迁移版本、事务、备份和只读历史导入。
- 打通准备、授权、执行、回读、结果、恢复及精确反向变更。计划变化或关键平台状态变化时，重新评估授权是否仍有效。
- 实现单一任务宿主及浏览器所有权，验证 GUI/CLI 同时请求、入口退出、宿主崩溃和重启核验。
- 保留现有操作界面，增加计划和任务页；业务校验逐步从 GUI 移入用例。

**通过条件：** 试点在 GUI/CLI 行为一致，状态落盘与外部结果可区分；所有权和故障恢复测试通过。M4 完成 MCP 对照后，才将第一项能力标为“三入口迁移完成”。

### M3：完整档案与多人归集

**交付：** 现有智能表格回传与收集链路的完整档案扩展、明细查询、补传与完整性核验；档案包用于补交和备份。

- 先核实当前表格结构、权限和接口容量/附件能力，按第 5.3 节决定明细与附件具体落点，记录归集 ADR。复用现有平台为首选，不预设必须改成手动导入。
- 用 M2 的完整任务档案贯通“落盘—投递—明细查看—收集核验”。保留旧版摘要通道，使用 schema 版本区分新旧客户端。
- 扩展字段映射、任务/条目/事件 ID、附件清单、可靠发件箱、明确拒收状态以及收集端分页/去重/冲突检查。
- 验证断网补发、响应超时但远端已写入、部分拒收、超大内容、附件缺失、重复与冲突、查询超过单批上限等情形。
- 统计视图继续从允许公开的字段派生；明细在原平台合适的表内查看，本地归集页面只补现有入口确实缺失的能力。清理与当前主链路不符的旧注释，避免未来 AI 误读历史方案。
- 补齐档案包导出/导入和旧数据导入，历史缺失字段明确说明；不要求同事日常手工交文件。

**通过条件：** 两个隔离的客户端数据目录产生的完整任务能经验证过的现有平台通道自动归集，明细与附件完整可查；重复不翻倍、拒收不假报成功、冲突可见。未验证的附件/容量能力明确列为待完成，不能仅凭摘要上报成功宣布完整归集完成。M5 每迁移一项功能，都补齐它的完整档案。

### M4（仅规划）：开放本地 MCP，提供 AI 使用指南

**交付：** 本地 MCP 启动/连接配置、版本化工具契约、配套 Skill、安装与使用说明、AI 调用验收案例。

#### M4.1 用户最终怎样使用

用户在支持本地 MCP 的 AI 客户端说：“把策略 A 中名称含‘测试’的价格配置关闭。”AI 通过助手查询实际账号、策略和配置，补充缺失条件，生成草稿计划。用户可以在原助手的计划页查看目标与差异；确认后由助手执行，AI 获取同一份进度和核验结果。

现有表单入口继续可用。用户可以全程手动填写，也可以让 AI 准备后再在表单里修改。修改目标、范围或方向会产生新计划，旧计划不能继续执行。用户无需为了使用 AI 将原本可正常工作的浏览器适配器换掉。

M4 以 M2 已完成的价格策略批量开关为执行试点。其他功能可以列出用途与迁移状态，但尚未完成验收时不向模型伪装为可执行工具。M5 每迁移一项，就接入相同机制。

#### M4.2 AI、MCP、Skill 和业务程序各负责什么

| 部分 | 职责 | 本轮实现方式 |
|---|---|---|
| 外部 AI 客户端/模型 | 理解自然语言、选择能力、询问缺失条件、解释工具结果 | 使用用户已有且支持本地工具的宿主，不要求助手内置另一个模型 |
| MCP 入口 | 发布工具说明、校验协议数据、调用共享用例、返回结构化结果 | 采用官方 Python SDK 的经验证版本，版本锁定；使用 stdio |
| Skill | 说明发现能力、补参、查看计划、执行和处理未知结果的操作顺序 | 一份简洁使用指南，附示例；适用能力/契约版本明确 |
| 应用与领域层 | 规则判断、计划、授权检查、任务执行与恢复 | GUI/CLI/MCP 共用；不依赖模型自觉遵守说明 |
| 平台适配器 | 查实际对象、调用平台或操作页面、回读结果 | 沿用可用适配器；模型无须接触 Page、CSS 或 SQL |

采用 [MCP 官方 Python SDK](https://github.com/modelcontextprotocol/python-sdk)处理协议，避免自己实现 JSON-RPC 通信细节。工具参数和结构化结果使用 [MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)的 schema 能力；项目自身仍要实现业务规则、授权与持久化，这些不会由 SDK 自动提供。

#### M4.3 第一批具体工具

下列名称是拟议业务工具，不是已经实现的函数，也不是 MCP 强制规定的名称。每个写入口只消费存档计划，不能让 AI 直接传入任意脚本执行。

| 工具 | 输入与作用 | 输出/副作用 |
|---|---|---|
| `assistant_status` | 查询助手、执行宿主及所需登录状态 | 是否可用、当前任务、缺失前提；不返回登录凭据 |
| `list_capabilities` / `get_capability` | 查询功能目录或指定功能 | 中文用途、字段、范围、例子、版本、可用状态 |
| `pricing_list_strategies` | 使用已核实的账号/环境，按名称或 ID 查策略 | 实际候选及分页信息；多个匹配交用户选择 |
| `pricing_prepare_toggle` | 方向、策略范围、选行方式及相应参数 | 校验错误，或存档计划、逐项差异、跳过与未知原因；不写平台 |
| `get_plan` / `show_plan` | 读取计划或让本地助手展示它 | 完整计划、中文摘要、授权状态；展示不等于批准 |
| `execute_plan` | `plan_id` 与调用请求 ID | 验证计划、有效授权和前置状态，创建/返回唯一关联任务，可能写平台 |
| `get_job` | 任务 ID、事件游标和分页参数 | 逐项进度、业务结果、证据引用及独立的归集状态 |
| `cancel_job` | 任务 ID | 取消可停止的后续步骤；已发生的提交保持真实状态 |
| `reconcile_job` | 任务 ID | 回读在途/未知步骤并更新本地核验记录，不重新提交 |
| `prepare_recovery` | 任务 ID | 对已明确可恢复的项生成恢复计划；未核验项继续待核查 |

每种业务提供有明确字段的准备工具；执行和任务查询共用固定接口。`execute_plan(plan_id)` 只执行已经固化的业务意图，不能携带新的业务参数覆盖该计划。输入相同请求 ID 重放时返回原任务；即使用新请求 ID 重复提交已消费的计划，也不能重新创建一轮写入。

#### M4.4 价格策略试点的真实字段如何整理

保留现有 YAML、`ModeSpec` 和规则中的信息，提升为一个版本化能力定义；不把当前混合了界面、页面定位和业务描述的 YAML 直接整个传给模型。

| 输入 | 当前能力 | 新契约如何表达 |
|---|---|---|
| 方向 | 开启/关闭 | 明确枚举；不会因缺参自动取开启 |
| 策略范围 | 当前策略页/指定策略 | 当前页先解析并固化实际账号、环境和策略 ID；不把“当前页”留到执行时重新猜 |
| 选行方式 | 关键词/本工具配置过的/清单 | 明确枚举，各自有条件必填字段 |
| 关键词或清单 | 字符串拆分和名称匹配 | 保留原匹配规则，在计划中展示实际命中对象和匹配方式 |
| 历史时间范围 | 按台账筛选所用日期 | 仅在适用范围出现；校验日期与时区口径 |
| 全部对象 | 旧关键词为空会匹配全部 | 保留显式“全部”选择；不能把 AI 漏填关键词当成用户授权全选 |

已存在的规则，例如“已是目标状态则跳过”“开启时人群选组为不限则跳过”，进入领域层；页面按钮文字和对象查找进入适配器。规则来源包括 `pt_runner.py:126` 的范围选择、`:170` 的分类，以及 `config/forms/价格策略批量开关.yaml`。未知状态不会由模型补成开启或关闭。

大批量计划可分页查询，摘要必须含总量、被截断/分页提示、跳过和未知项，完整清单保存在助手中。后续 Excel 功能在本地导入文件并返回 `input_id`，AI 引用已登记输入；不会假定聊天附件天然就是助手可读取的本机路径。

#### M4.5 确认和执行的具体交互

1. AI 提交草稿参数；助手进行确定性校验与只读查询，返回缺失字段或已保存的计划。
2. `show_plan` 将同一计划展示到原桌面界面。首期普通宿主使用这里的可信确认；若已存在可验证且覆盖本计划的授权，则复用，不重复询问。
3. 用户确认绑定计划摘要/版本、账号、对象和动作。AI 传来的 `confirmed=true` 或“用户刚才答应了”不作为凭证。只在聊天里说“确认”能否直通，需要具体宿主提供可验证的交互记录；不能假定 MCP 自带跨宿主的可信用户确认。
4. 执行宿主再次核验账号、对象和关键前置状态；如有实质变化，返回新计划待核对。队列中的任务同样执行这一步。
5. 对计划逐项执行并回读。聊天断开后任务由助手宿主持有；重新连接可查原任务。账号失效、机器退出等情况显示实际中断状态。
6. 返回“已核验成功/失败/跳过/待核查”和具体下一步；M3 的智能表格回传异步进行，其失败不改写业务结果。取消和恢复分别记录，不能称作自动撤销。

模型无法被 schema 保证永不误解，因此把关键限制写入工具说明，并在程序中执行。日志去 stderr 或本地日志，stdio 的 stdout 只承载协议数据；避免现有 GUI/CLI 打印污染 MCP 会话。

#### M4.6 按四个小迭代实现

| 小迭代 | 开发内容 | 可审阅交付 |
|---|---|---|
| M4-A | 试点字段与错误契约、能力目录 | 同一输入在表单与工具里的字段/规则对照，离线可查询 |
| M4-B | 本地 MCP 桥接、状态/选项/计划/结果查询 | 能连接、能补参、能显示真实候选与计划；尚不开写入口 |
| M4-C | 执行、授权绑定、请求防重、取消/核验/恢复 | 价格策略开关的完整受控闭环，GUI/CLI/MCP 行为对照 |
| M4-D | Skill、客户端配置示例、连接自检、宿主验证 | “设置—AI 接入”中的启动配置和诊断；两个可用宿主的实际验收记录 |

使用与现有桌面构建相容的控制台 MCP 启动入口，验证 Windows 路径、编码、进程退出与运行时依赖；不得假定无控制台的 GUI exe 自动具有可用 stdio。普通用户无需安装完整开发环境。MCP Apps 作为支持宿主的可选交互增强，文字结果与本地计划页始终可用。

**验证场景：** 完整输入、缺条件字段、错单位、同名候选、空关键词、账号变化、过期计划、重复请求、重复计划、客户端断开、写入超时、取消后已完成项、恢复计划、业务成功但回传失败。比较三入口的规范化业务意图和结果，不要求时间戳或随机 ID 相同。真实写入只跑一个路径，其他入口用相同夹具对照。

**通过条件：** 试点三个入口使用同一用例，缺参/过期计划/无有效授权不能触发写入；AI 和用户能获得相同执行事实；不支持的宿主能力有明确说明。

### M5（仅规划）：迁移其余功能，同时精简并评估 API 替换

**交付：** 第 3 节全部功能的新路径、各功能契约与档案、精简记录、平台适配选择及验证证据。

M4 建好工具协议和交互通路，M5 将其推广到全部功能，并完成业务内部的拆分与精简。每项迁移同时覆盖前端、CLI、MCP、记录和归集，不能只给旧 runner 包一层 MCP 就宣称完成架构重构。

#### M5.1 每项功能都按同一套步骤迁移

| 步骤 | 实际改动 | 该步留下的证据 |
|---|---|---|
| 1. 固定现有行为 | 盘点表单、模板、范围、分步/暂停、输出和恢复；追踪注册表与调用入口 | 功能矩阵和脱敏样例，标出已确认 bug 与有意兼容 |
| 2. 抽出领域规则 | 从 runner/前端/YAML 中提取资格、范围、日期、状态判定等纯规则 | 规则来源、类型化输入输出、正常/边界/非法输入测试 |
| 3. 抽出应用用例 | 把读取、预检、计划、提交、回读、恢复和记录接入共用任务流程 | 每个提交点的状态转换与失败恢复依据 |
| 4. 保留并封装平台适配 | 原有能工作的页面操作先通过业务端口接入；按需替换 API | 原始响应/页面到标准业务结果的映射与兼容说明 |
| 5. 接通三个入口和归集 | 更新桌面桥接/CLI/MCP 准备工具，共用能力定义；生成完整档案 | 同样输入的三入口对照、实际配置/记录/结果回传检查 |
| 6. 核验并切换 | 离线回归后，在已授权平台对象上验证关键业务路径 | 前后状态、任务档案、失败和恢复结果；按功能切换新实现 |
| 7. 精简旧实现 | 删除已被替代的规则与编排，提取真实重复，缩小存量清单 | 被删模块/函数的替代关系、动态引用和打包检查、回退说明 |

已有 `ModeSpec` 保留为迁移接线点，并逐步连接新能力定义和用例工厂；保留懒加载，避免启动时加载所有业务依赖。新核心不导入旧 runner；确需复用旧代码时，通过 `adapters/legacy` 过渡。通用旧 runner 服务多个功能，只有最后一个依赖它的功能迁完后才能删除。

“拆文件”以职责为依据：`webapp.py` 留桥接与 UI 事件；规则进入 domain；任务逻辑进入 application；CSV/Excel/数据库/页面操作进入 adapters。`app.js` 按功能区域拆分，但现有表单与流程入口保留，先验证本地加载与打包，不同时迁移整套前端框架。

#### M5.3 多步骤功能怎样恢复

以资源位投放为例，应用层表达“校验素材与范围 → 创建/确认活动 → 创建/确认单元 → 配置创意 → 核验”，每步保存使用的输入、平台对象 ID 和结果。页面如何定位按钮由适配器负责。

若活动已创建、单元创建时超时：先查询单元是否已存在。核验存在则记录对象并续跑；明确未创建且前置条件仍成立时才生成相应恢复动作；无法判断则停在待核查。不能从头再次创建活动，也不能超时后换 API/浏览器重发一次。

同样的任务与状态设施可用于授权或会议，但“如何判断对象已创建”“申请何时生效”“预约时间/名额规则”属于各自领域和平台适配，不能抽成一个猜所有页面的巨型 runner。

#### M5.4 API 替换怎样决定

分层迁移先复用当前可工作的交互方式；API 替换作为可以单独验证的小改动，每个功能形成一张适配决策记录：

1. 是否有稳定可用的接口，登录、权限和签名从哪里来。
2. 接口能否表达全部现有字段，是否与页面采用相同业务校验。
3. 是否能查询提交结果、定位实际对象，如何处理重复请求和超时。
4. 对照样例与受控真实任务通过后，才切换该项适配器。

可独立认证的 API 可减少浏览器依赖；需要登录上下文或页面签名的接口继续通过浏览器会话；其余保留 Playwright。会议现有签名依赖应继续封装，不能把去掉浏览器当作 M5 完成指标。

#### M5.5 自制流程怎么接 AI

保留现有录制—编辑—试跑—送审/收编路径及 `config/flows` 数据，通过版本化流程定义迁移。旧流程的 `click`、`fill`、`press` 等词汇继续由适配器解释，新增每步“只读/可能写入/明确写入”、预期结果、超时和核验要求。

不能仅凭 `submit: true` 判断所有写入：回车、勾选、失焦或某些页面跳转也可能触发业务变化。未识别副作用的步骤不得标为只读试跑；需要真实演练时保留该能力并明确记录实际变更。

AI 日常执行引用已经登记、验证、允许使用的流程 ID 与版本，输入符合该流程字段契约。草稿仍可本地编辑和受控试跑，但模型临时拼出的步骤不能自动取得正式执行资格，传入 `status=adopted` 也不能绕过验证。以后可让 AI 协助整理流程草稿，审核与发布仍走同一生命周期。

#### M5.6 每批交付和停止条件

每批交付功能演示、行为对照、源码变化、精简清单、归集样例和验证报告。只有该批通过，才标记对应能力可用；其他未迁移功能仍可从原入口使用。

以下情况不能切换默认新实现：无法解释字段差异；模板/范围/原有合法模式丢失；任务记录或归集缺失；平台超时会造成重复提交；正常操作必须依靠模型猜测规则。此时保留旧入口并继续修复，不能用缩小验收范围让批次通过。

不让新旧路径同时对同一业务对象真实提交；对照在离线夹具、只读结果与单路径受控实测中完成。验收后删除被替代逻辑；需要暂留的兼容层有明确依赖和退出条件，避免长期维护两套同义实现。

**通过条件：** 14 项内置功能和自制流程都已完成上述闭环；旧兼容层只剩有明确原因、负责人和退出条件的部分；不再复制三套业务规则。真实环境未验证的功能不能被宣称已完整迁移。

- 保持运行代码在 `src` 等现有有效载荷范围内，检查新增前端资源/配置/Skill 的分发方式。新版本通过健康检查前保留可恢复备份。
- 在具备仓库配置权限、准备发布时运行远端质量工作流并设置受保护分支的必需检查；合并路径包含验证结果，不能仅依赖本地提示文件。
- 从维护者自己的受控小任务试用开始，再让少量同事验证安装、各自登录、完整档案交付及归集，最后扩大使用。

**通过条件：** 第 11 节全部验收项有证据，已知会漏项、重复提交、虚假成功或丢失数据的问题没有未解决的发布阻断项。没有实测的场景明确登记，不能用离线脚本通过替代真实平台和安装验收。

### 阶段节奏与投入

M0 → M1 → M2 → M3 → M4 → M5 → M6 为推荐顺序。测试、规范、数据迁移和文档随每阶段进行，不留到最后补。一个阶段通过后继续已授权范围内的工作；普通实现选择不需要逐项再次确认。

先以 M2—M4 的完整试点测出每项迁移的实际工作量，再细化后续排期。目前不承诺缺少真实环境依据的固定工期。影响周期的主要因素是平台登录/接口变化、历史配置样本、多步骤提交语义和实际业务验收窗口；不能只用文件行数估算。

## 9. 功能保留、验证与回退方法

### 9.1 如何证明精简没有破坏功能

- 建立固定的脱敏输入、规范化配置和预期操作意图；旧/新实现用这些数据比较字段、目标、顺序、跳过理由及结果含义。对已经确认的旧 bug 使用修正后的独立预期，不能把旧错误当标准答案。
- 对读取与纯计算使用差异测试；对真实写入只执行一个路径，用受控对象核验前后状态。禁止为了对比而让新旧引擎同时提交同一业务任务。
- 对每项变更选择相关失败场景：写盘失败、失联、重复请求、账号切换、部分成功、计划过期、附件缺失、升级失败等，避免只测成功路径。
- 页面适配需要页面/响应样例和实际环境核验；原有 18 个脚本的检查数量不能代表完整覆盖率。
- 性能在相同样例和环境下对比启动、表格解析、计划生成及必要的端到端耗时；以条件等待、批量只读查询和按账号/环境隔离的缓存优化。缓存用于展示和准备，写入前核验不依赖过期值。不能靠缩短等待硬凑速度。
- 分模块报告重复实现数量、已移除旧路径、残留兼容项和打包体积。新功能确有必要的代码增长单独解释，不能以总行数决定成败。

### 9.2 故障与回退

- **平台操作：** 取消不代表撤销。可逆操作生成明确反向计划，只有当前状态仍符合该任务的修改结果时才应用；不可逆或无法核验的变更提示人工处理，不伪装数据库式回滚。
- **代码切换：** 按功能启用新路径；发现问题先停止该功能的新写入。只有旧实现兼容当前数据且不会盲目重做在途任务时才回退，否则保持只读排查。
- **数据迁移：** 先备份，验证新库再切换，旧文件不立即删除。旧数据缺少稳定身份时保留来源和不确定性，不自动恢复执行。
- **版本降级：** 程序回退必须连同数据库版本一起评估。新版本运行后已产生的新记录不能通过直接覆盖旧库丢弃；需要导出新增档案、核对外部在途操作，再决定恢复兼容快照或修复向前迁移。
- **备份：** 使用一致性备份流程，验证库和附件都能恢复；避免复制正在写入的单个数据库文件而遗漏关联状态。

## 10. 后续 AI 迭代必须遵守的规范

### 10.1 已准备的约束

规范入口为 [AGENTS.md](../../AGENTS.md)，`CLAUDE.md` 引用同一入口；旧项目说明保存在历史地图中。实际规则见[架构规范](ARCHITECTURE.md)、[开发规范](DEVELOPMENT.md)、[业务契约](CONTRACTS.md)和[执行说明](ENFORCEMENT.md)。

| 约束 | 提醒/规范 | 程序化检查或验收 |
|---|---|---|
| 新代码按层组织 | 目录、职责和依赖方向 | 架构 AST 检查、循环依赖检查 |
| 核心不直接操作外部系统 | 通过应用层端口 | 导入边界与常见直接 I/O 检查；复杂语义仍需 review |
| 旧债不能无限扩大 | 80 个旧文件精确清单 | 新平铺模块失败；迁移后缩小存量清单 |
| 状态与结果真实 | 稳定 ID、未知状态、回读、授权与计划绑定 | 对应业务/故障测试；不是文档写了就算实现 |
| 不为过检查削弱规则 | 不删测试、不加宽泛豁免、不关闭 CI | PR 审阅、规范变更 ADR、质量工作流 |
| 发版先检查 | 统一检查命令、版本与迁移要求 | 本地构建、手工发布脚本、发布工作流接质量门禁 |

统一命令：

```text
python tools/check_project.py --static-only
python tools/check_project.py
```

### 10.2 “强制”的实际边界

AGENTS/CLAUDE 是开发指令，不能保证任意 AI 或使用者绝不偏离。静态检查也不能证明所有业务语义正确。可执行的约束是：**违规时检查失败，构建/发布失败；远端受保护分支要求质量检查通过后才能按正常流程合并。**

本地检查器、工作流和脚本已准备，远端 CI 尚未运行，分支保护尚未设置。仓库管理员仍可能拥有修改规则或绕过保护的权限；如要限制这类权限，需要在实际仓库设置中决定。不能把提示词文件描述成不可绕过的安全机制。

以后每次 AI 迭代按这个闭环交付：读规范和实际代码 → 指明需求与层次 → 最小可验收改动 → 运行相关验证和必要完整检查 → 更新说明 → 报告结果与未验证事项。只有架构边界、授权/恢复语义、数据位置或部署边界改变时记录 ADR；普通实现无需重复征求批准。
