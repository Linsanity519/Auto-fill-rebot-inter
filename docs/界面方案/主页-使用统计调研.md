## 0. 结论先行

三句话：

1. **最难的不是画图，是「多少人」这三个字。** 这是个离线 exe，整个文件夹拷给同事各跑各的，
   彼此不通信，也没有任何服务端。想统计到人，必须先决定「数据往哪汇」—— 见 §2.5。
2. **「省了多少时间」= 人工基准 × 条数 − 机器实跑。**（2026-08-21 改的口径，
   原来是「机器跑了多久就算省了多久」—— 那等于把人当成和脚本一样快，
   把这工具的价值自己压掉了一大半。）见 §2.4。
3. **分三步走**：埋点（已完成）→ 主页读本机数据 → 填上共享目录变成全团队数据。
   一上来就上服务端是过度设计，百人规模用不着。

## 1. 现状盘点：手上已经有什么

| 已有 | 在哪 | 能不能直接用来统计 |
|---|---|---|
| 每条记录的成败明细 | `output/result.csv` | ✗ **每次跑都是 `"w"` 覆盖写**（[runner.py:245](../../src/runner.py:245)），只剩最后一次 |
| 断点：done / failed | `output/state.json` | ✗ 只是「哪几行做过」，没有时间、没有历史，用户还会主动清 |
| 运行日志 | `output/run.log` | △ 是追加的，有时间戳，但内容是异常栈和零散 info，**跑了几条/成功几条并没有写进去** |
| 每个字段的耗时 | `run.log` 里 `填「X」花了 N 秒`（[wizard_filler.py:107](../../src/wizard_filler.py:107)） | △ 只有 wizard 有，且只记慢的那些 |
| 界面上的运行日志 | 只推给前端，**不落盘**（[webapp.py:106](../../src/webapp.py:106) `WebUI.log`） | ✗ 关掉窗口就没了 |

**结论：现在等于零基础。** 没有任何一份文件能回答「这台机器上这个工具总共跑过多少条」。
所以第一步必然是新增一份埋点，而不是从现有文件里刨。

一个好消息：埋点位置很干净。六个 Runner 各写各的（`Runner` / `DmpRunner` / `AbRunner` /
`WizardRunner` / `AdRunner` / `MeetingRunner`，互相不继承），但它们对外长得一模一样 ——
`run(records) -> list[dict]`，每个 dict 都有 `状态` 字段。而新界面所有配置类型的运行
**都从同一个函数进出**：[webapp.py:485 `Api._run`](../../src/webapp.py:485)。
在那儿包一层就能覆盖全部七种配置类型，一个 Runner 都不用改。

⚠ 三个入口要分别看：`Api._run`（新界面，默认）、`main.py --cli`、`gui.py --tk`（备用界面）。
建议只埋前两个，`--tk` 那条路加个 TODO 就行 —— 它本来就是「新界面出问题时退回去用」的。

## 2. 怎么统计

### 2.1 埋什么事件

一条运行一条记录，追加写 `output/usage.jsonl`（JSON Lines，一行一个事件，
崩溃了也不会毁掉整个文件，这点比 JSON 数组强）：

```json
{"ts":"2026-08-20T14:03:11+08:00","event":"run_finished","uid":"a3f1c2","ver":"1.0.0",
 "os":"windows","run_id":"9f3a…","form":"DMP延期","mode":"auto","scope":"active",
 "total":37,"ok":35,"failed":1,"skipped":1,"dry":0,"seconds":412.6,"wait_seconds":8.3,
 "stopped":null,"chrome":"151.0.7922.138","entry":"webui",
 "fail_kinds":{"timeout":1},"fail_stages":{"单元层":1},
 "item_p50":9.8,"item_p90":24.1}
```

**2026-08-20 补的几组字段**（都遵守「不记业务内容」那条铁律）：

| 字段 | 回答什么问题 | 怎么保证不泄漏业务内容 |
|---|---|---|
| `fail_kinds` | 失败是超时、找不到元素、还是被页面拒了 | 输出**固定枚举**（`timeout` / `selector_miss` / `page_rejected` / `empty_required` / `browser_lost` / `other`），错误原文只在内存里过一遍分类器，一个字都不落盘 |
| `fail_stages` | 卡在活动层 / 计划层 / 单元层 / 创意 | **白名单匹配**，只有命中这几个词才输出 |
| `item_p50` `item_p90` | 是整体慢，还是个别卡死 | 纯数字。逐条耗时在 `WebUI.progress` 里掐表拿到（六个 Runner 都会调它），**一个 Runner 都没改**；且同样扣掉了等人确认的时间 |
| `stopped` | 是跑完的还是中途停的 | 布尔 |
| `chrome` | 挂的浏览器什么版本 | 版本号 |
| `dpi`（在 `app_open` 上） | 屏幕缩放多少 | 数字。界面在高 DPI 下错位过一次，再有人报错能直接对号 |
| `bad_fields`（在 `load_checked` 上） | **模板哪一列最容易填错** | 只取「列名：说明」冒号左边那半截 —— 列名是模板表头；右边经常带着用户填的值（「『年度大会员VIP』不是有效值」），绝不带出去 |

⚠ 唯一「看过错误原文」的地方是 `usage._fail_kind()`，它的出参只可能是上面那几个枚举值之一。
改那段代码时先读它上面的注释。

⚠ `form` 记的是 yaml 的 `name`（也就是文件名），**不是侧栏上显示的 label**。
label 改名了历史数据还对得上，主页展示时再查 `nav.label` 翻译成人话。

建议同时埋的几个轻事件（都很便宜，但少了会答不上问题）：

| 事件 | 回答什么问题 |
|---|---|
| `app_open` | 打开了但一条没跑 = 有人试了没跑起来。**发现率和流失都藏在这个差值里** |
| `template_made` | 谁在生成模板却没执行 —— 通常卡在「模板填不明白」 |
| `load_checked` | 载入并检查了多少条、有多少条校验不过 = 数据质量 |
| `run_finished` | 主力指标（上面那条） |
| ~~`run_stopped`~~ | 不用单独埋：点停止后 `run()` 是正常返回的，照样落一条 `run_finished`，从 `ok + failed + skipped < total` 就能看出是中途停的 |

⚠ **只记数量和状态，绝不记业务内容**。人群名称、价格、活动ID、会议室主题一律不进埋点。
理由有两条：一是这份文件将来要汇总到公共位置，二是 `output/` 已经因为含业务信息被
`.gitignore` 排除了（见 [.gitignore](../../.gitignore)），别在新文件上重犯。

（AB 那边「这实验压根不能延期」是没事可做，不是做失败了，算进 failed 会平白拉低成功率）。

### 2.3 「多少人用过」：身份（已定 —— 只匿名）

工具是离线的、没有登录，所以要造一个「人」的概念。**已定：只用匿名指纹，不做实名。**

实现（[usage.py `_uid()`](../../src/usage.py)）：`sha1(用户名@机器名)` 取前 8 位。
用户名和机器名**不落盘**，落的只有那 8 位 hash。它只够干两件事 ——
数「有多少个不同的人」、认出「哪条是我自己的」，反推不回是谁。

- 8 位（32 bit）在百人规模下撞库概率约十万分之一，够用。
- 一人多机会被算成两个人。**接受这个误差** —— 想修就得实名，不划算。
- 开关：`config/settings.yaml` 的 `usage.enabled: false` 可整个关掉。

⚠ 匿名不只是隐私考虑，也是产品考虑：这个工具一旦能看出「谁没在用」，
性质就从「帮大家省时间」变成「监控」，愿意用的人反而会变少。所以
**主页不做点名排行榜**（见 §3.2 模块⑤）。

### 2.4 「省了多少时间」：口径（2026-08-21 改过一次）

**现在的口径：**

```
人工要花 = 人工基准(这个配置类型, 一条多少秒) × 成功条数
机器实跑 = 本次墙钟耗时 − 等人点确认的时长          ← 这半截仍然是实测
省下工时 = 人工要花 − 机器实跑                      ← 负数按 0 算
累计     = Σ 每次运行（重跑那次不计，见 §5 坑1）
```

人工基准写在 `config/settings.yaml` 的 `usage.saving.per_item_seconds`，一个配置类型一个数，
谁都能改。**埋点文件里存的永远是实测秒数，换算只在显示时做** —— 基准改了，
历史数字跟着一起重算，不用回头补数据。

**基准本身是算出来的，不是拍的** —— [tools/human_baseline.py](../../tools/human_baseline.py)：

```
一条 = Σ(每个字段 × 按控件类型的单价) + 每条固定开销
```

字段清单直接来自 `config/forms/*.yaml`（那本来就是「这个表单有哪些字段、每个是什么控件」的
完整记录）；单价按控件类型定，脚本里每一行都写了理由 —— 封面 90 秒（含手动压到 700KB
以内，机器是自动压的）、图片上传 45、起止日期 35、多选 15、下拉 10、文本 8。
reveals 展开出来的条件字段按 **0.5 个**算：一条单元只会走中其中一个分支。
DMP延期 / AB实验延期 没有字段清单（是「翻列表找到这行 → 点几下 → 一个月一个月试最晚可选日」），
按 runner 实际走的动作逐条列。

⚠ 两个刻意的取舍：

- **静态数字，不在运行时实时算。** 实时算的话 yaml 一改历史数字就跳，
  「上周报的 12 小时今天怎么变 14 小时了」没法解释。所以脚本只负责让这个数**可复算、可质疑**，
  结果手动抄进 settings.yaml。
- **资源位投放取所有资源位的平均**（短信 132 秒 vs 播放页催费条 422 秒，差三倍）。
  想精确到资源位就得把资源位名称写进埋点 —— 那是业务内容，违反 §2.3 的第一条铁律；
  而且几十条一批平均下来误差会摊掉。

校准办法：找人拿秒表真做一条，和脚本算的对一下。差得多**改脚本里的单价，别改结果数字** ——
改了结果就又变回拍脑袋了。单价是「一个下拉要点多久」这种和具体表单无关的量，
校准一次可以复用到所有配置类型。

<details>
<summary>为什么推翻了原来「机器跑多久 = 省多久」的口径</summary>

原来的理由是「实测比估的可信」，这条本身没错，但它把人当成了和脚本一样快：
人在页面上填一条资源位单元要翻三段表单、几十个字段，脚本二十秒的事人工得七八分钟。
照原口径报出去，这工具的价值被自己压掉了一大半 —— 保守到失真也是一种不准。

**也没有采用「机器耗时 × 2 或 × 3」这种倍数**（一开始想的是这个）：倍数会跟着脚本快慢
反着走 —— 脚本优化快了，报出来的「省时」反而变少（`e6a8533` 那次优化就会让数字掉下去）；
某次网络卡了十分钟，倒成了大功一件。人工基准和脚本快慢无关，它衡量的是这件事本身值多少时间。
真想要倍数口径也留了口子：`usage.saving.mode: multiplier`。

⚠ 界面上那行小字必须把两半分开说清楚：**人工那半截是估的，机器那半截是实测的**。
一句「省下 12 个工作日」没人信，「人工要 15 天 − 机器实跑 6 小时」才站得住。
</details>

⚠ 「机器实跑」那半截要处理的坑：**「逐条确认」模式下人是坐在旁边看着的**，那段时间不算机器替你干活。
所以埋点把「等人点按钮」的时长单独记了一列（`wait_seconds`，
见 [webapp.py 的 `WebUI._waiting`](../../src/webapp.py)），主页展示时减掉。
减完之后三种模式的口径就一致了：

| 运行模式 | 记的 `seconds` | 记的 `wait_seconds` | 主页算作机器代劳 |
|---|---|---|---|
| 全自动 | 全程 | 0 | 全程 —— 人真的可以走开 |
| 逐条确认 | 全程 | 等确认的那部分 | 全程 − 等确认 |
| 空跑 | 全程 | 可能有 | 同上，但**只做参考不计入累计**（一条都没提交） |

**预定会议室仍然要单独一套口径**。它一次运行就几百毫秒，按时长算等于没有价值，
但它的价值恰恰最大 —— 是「00:00 那一刻抢没抢到」。对它单独统计
`抢中次数 / 尝试次数` 和 `抢到用时`，展示成「帮大家抢到了 N 间会议室」。

### 2.5 数据往哪汇（**最终：群机器人 webhook 上报 + 快照分发**，2026-08-21）

> 这一节改过三次，把三次的结论和为什么被推翻都留在这儿，别再走回头路。
>
> ① 共享目录 → 推翻：公司没共享盘，同事也访问不了 ML 平台 proxy（实测）
> ② 企业微信在线表格（浏览器自动化）→ **推翻，见下面 2.5.1**
> ③ **群机器人 webhook 上报 + 收集端 MCP 整理 + 快照随包分发** ← 现在这个

#### 2.5.1 为什么推翻了「浏览器操作企微文档」（2026-08-21）

它能跑通，实测数据也漂亮（写 3.6 秒、读 2.7 秒）。推翻它的不是性能，是**可靠性模型**：
那套东西每一环都要求「前端有人、有登录态、页面结构不变」。实际后果是
**有人用了一整天，团队表里一条没有，而且没有任何人知道** —— 失败是静默的。
三个原因叠在一起：上报只在跑完后触发且是后台线程（关窗口就没了）、失败只写日志、
只报最近两周（失败超两周就永远补不回来）。

给上百个人用的东西，不能建立在「浏览器状态正常」这个前提上。

#### 2.5.2 现在的链路

```
同事的机器（只有 webhook key）          你的机器（唯一持有 MCP key）
usage.jsonl → webhook POST → 统计群  →  全选复制 → 收集脚本 → 智能表格 + team.json
                                                                    ↓ 随包分发
                                                        同事 EXE 首页「截至 X/X」
```

| 环节 | 怎么做 | 为什么不能更好 |
|---|---|---|
| 上报 | `urllib` POST 群机器人 webhook，3 秒超时 | — |
| 群 → 文档 | **手工全选复制 + 双击一个 bat** | 群机器人只写不读；MCP 机器人是被调用的工具，不会盯着群；「会话内容存档」要管理员开通 + 解密 SDK |
| 同事端看团队数 | 随包分发的 `config/team.json` 快照 | 读文档要 MCP key，而那把 key 没法限权（见下），不能分发 |

⚠ **企微文档 MCP 机器人的 apikey 没法限权**（2026-08-21 确认）：一把 key 覆盖持有人
名下所有文档，能 `doc_create` / `doc_contents_overwrite` / `sheet_subsheets_delete`，
也不能用专用账号建。所以它只能留在收集端，绝不能进分发包 —— exe 里的字符串谁都能翻出来。

MCP 本身的实测结论（`tools/mcp_doc.py`）：
- 端点 `https://qyapi.weixin.qq.com/mcp/v2/bot/doc?apikey=…`，**纯标准库可调**
- 返回的是普通 JSON 不是 SSE，也不需要 `Mcp-Session-Id`，比协议文档说的简单
- `tools/list` 62 个工具；写用 `smartsheet_records_update`，读用 `smartsheet_records_list`

#### 2.5.3 存档：浏览器方案踩过的坑（代码已删，经验留着）

万一哪天又要驱动企微文档页面，这几条是实测出来的，别再踩一遍：

1. 合成的 `Ctrl+V` **不会**让浏览器去读系统剪贴板，必须走 CDP 的
   `Input.dispatchKeyEvent` + `commands:["paste"]`。复制、全选同理。
2. 定位单元格一律用名称框（"A5" 这种地址），**绝不用像素坐标** —— 每个人的屏幕和
   窗口大小都不一样，写死的坐标在别人机器上会点空。
3. 但「点一下网格」这件事省不掉：名称框回车后焦点回到 body，复制命令根本到不了表格
   手里（拿回来的是网页标题那几行字）。所以点击坐标要从 DOM 里量 canvas 算出来。
4. 顺序不能反：先点网格拿焦点，再用名称框选格。反过来点击会把选中格拉走 ——
   踩过一次，结果是数据行盖掉了表头。
5. 不授剪贴板权限的话 `navigator.clipboard.readText()` 会弹权限框**并一直挂着等人点**，
   表现是程序卡死不是报错（卡过两分钟）。而「访问此设备上的其他应用和服务」
   是 local-network-access，playwright 的 `grant_permissions` 不认，得走原始 CDP 的
   `Browser.setPermission`。
6. 全选会把下面几百个空行也复制回来（一行全是制表符），必须滤掉，否则「表里现在有几行」
   判断不出来，追加位置会跑到几百行开外。

#### 2.5.4 上一版（已废弃）的实测数据

⚠ 下面「共享目录」那一节是最初的方案，**已被推翻**：公司没有共享盘，同事也访问不了
ML 平台的 proxy 地址（实测）。最终走的是**企业微信在线表格**，实测结论：

| 验证项 | 结果 |
|---|---|
| 登录 | 在机器人那个 Chrome 里点一次「继续在浏览器中使用」，**不用扫码**（本机企微客户端自动带身份） |
| 权限 | `auth: 3`（可编辑）、`enable_corp_internal: true`（公司内部成员都能访问） |
| 写 | 选中格 → 系统剪贴板 → CDP `Input.dispatchKeyEvent` 带 `commands:["paste"]` → 一次贴 N 行，**3.6 秒** |
| 读 | 全选 + 复制 → 读剪贴板，拿到完整 TSV，**2.7 秒** |
| 持久化 | 硬刷新后数据还在 |

⚠ 两个必须记住的坑：合成的 `Ctrl+V` **不会**触发浏览器真正读剪贴板，必须用 CDP 的
`commands:["paste"]`；焦点停在名称框那个 input 里也白搭，得先点到网格上。

**结构（已定）**：一人一个工作表存明细 + 一个「汇总」表用跨表公式聚合，主页只读汇总表 ——
这样写完全无冲突，读也只要一次 2.7 秒（逐个切 100 个工作表要 4~5 分钟）。
花名存在受保护的列里。

### 附：最初的共享目录方案（留档）

**百人规模选 B（共享目录），理由：**

- 数据量小到可以忽略：一次运行一行 ≈ 200 字节，100 人每人每年跑 300 次 = 全团队 **6 MB/年**。
  为这点数据养一个服务不划算。
- **一人一个文件，永远只有自己在写**，天生没有并发写的问题 —— 这是 100 人这个规模上
  最容易被忽略、又最容易翻车的点（如果所有人往同一个文件里 append，迟早写坏）。
- 实现上走「整份覆盖 + 临时文件 + os.replace」，所以：上周没连上共享盘的事件，
  这周连上会**自动补齐**；别人读到的永远是一个完整版本，不会读到写了一半的文件。

⚠ 共享目录路径填在 `config/settings.yaml` 的 `usage.share_dir`，**留空就是只统计本机**。
分发包里默认留空 —— 路径定了之后改一次 settings.yaml 再打包，同事拿到就是通的。

下面是当初对比的四个方案，留档：


| 方案 | 怎么运作 | 成本 | 风险 |
|---|---|---|---|
| **A. 纯本地** | 只读本机 `usage.jsonl`，主页展示「我的战绩」 | 零 | 答不了「多少人用过」 |
| **B. 共享目录**（← 选了这个） | 每人一个文件 `{share_dir}/{uid}.jsonl`，整份覆盖；主页把整个目录读回来聚合 | 低，无服务端 | 盘不可达要能静默降级；**一人一文件天然避开并发写** |
| **C. 小服务端** | 客户端 POST 事件，主页查接口 | 中，要部署要维护 | 最规整，但为一个内部小工具养个服务，值不值得先想清楚 |
| **D. 企微机器人 webhook** | 跑完往群里播报 | 极低 | **只能播报不能查询**，当不了数据源，但很适合做周报（见 §6 阶段3） |

**走的是 A → B**：A 的埋点和口径已经落地（B/C 都复用这部分），
B 只差一个共享目录路径，D 留作周报的锦上添花。

⚠ B 方案的两个必须处理的细节：①共享盘不可达时**只失败不报错**，绝不能因为统计写不进去
挡住正经业务；②本地永远留一份，联不上时攒着，下次能连上再补传。

## 3. 怎么展示

### 3.1 放在哪

侧栏刚改成了「主 Tab + 分 Tab」两层。**主页不属于任何一组**，建议在「配置类型」标题
上面钉一个独立的「首页」项（带一个和分组项不同的视觉重量），点左上角 logo 也回主页。
第一次打开程序默认停在主页，而不是像现在这样直接落到第一个配置类型上。

### 3.2 主页模块（按建议优先级）

主页有两个受众，一屏里都要照顾到：**用的人**要一个「这玩意值得用」的理由，
**维护的人**要成就感和「下一步修哪儿」。模块①②③⑤⑦偏前者，④⑥偏后者。

**① 顶部四宫格 —— 一眼看到的数**

```
   累计处理        机器代劳         在用人数        一次做对率
    1,284 条      约 96 小时        11 人            94.3%
   本周 +173     ≈ 12 个工作日     本周活跃 6 人    近30天
```

⚠ 「机器代劳」下面必须有一行小字口径：`机器实际运行时长，已扣除等你点确认的时间`。
这行小字是这个数字可信不可信的全部区别 —— 而且按 §2.4 的口径，这句话是**实测**，
不是估算，经得起追问。

**② 大家在用什么 —— 横向条形榜**

按配置类型排，每行：`条数 · 占比 · 机器代劳时长 · 成功率`。
条形用条数排序，时长用数字标在右侧 —— 因为「条数最多」和「代劳最久」通常不是同一个
（DMP延期条数碾压，但资源位投放单条价值高十几倍），**这个反差本身就是主页最有信息量的一屏**。

**③ 趋势 —— 近 12 周柱状（堆叠按配置类型）**

回答「是越用越多还是三分钟热度」。比日粒度好：这类工具是「攒一批集中跑」，
日线全是尖刺和空洞，周线才看得出趋势。

**④ 我的战绩 —— 本机数据**

「你跑了 X 条，省下 Y 小时」+ **能力覆盖度徽章：7 个配置类型你用过 3 个**。
覆盖度这一项是顺便做功能导航 —— 很多人根本不知道这工具还能抢会议室。

**⑤ 谁在用 —— 人数 + 本周活跃**

默认**不做点名排行榜**（见 §2.3 隐私）。做成首字母头像墙 + 「本周 6 人活跃」，
自己那个高亮。要做榜单的话建议加个开关，且只显示前三名 + 自己的名次。

**⑥ 稳定性 —— 成功率（失败原因榜做不了）**

成功率做了（顶部「一次做对」+ 每个配置类型条形上的 tooltip）。

⚠ **失败原因 Top5 做不出来，而且是故意的**：错误信息里经常带着页面上的业务文案
（人群名称、活动名），埋点按 §2.1 的铁律没记错误原文，所以聚不了类。
真要这个功能，得先设计一套「错误分类」（超时 / 选择器失效 / 页面报错…），
只上报类别不上报原文 —— 那是另一件事，现在不做。

**⑦ 最近动态 feed（可选）**

`3 分钟前 · 某某 用「DMP人群延期」处理了 42 条`。有社交感、能让人知道工具是活的，
但只有 B/C 方案（有汇总）才做得出来，且要注意别把「谁在什么时间干了什么」暴露得太细。

### 3.3 空状态别忽略

新同事第一次打开，所有数字都是 0，这时候主页应该是**引导页**而不是空表格：
一句「这个工具能帮你做这 7 件事」+ 每个配置类型一行说明和跳转。
主页的第一价值其实是「让人知道有这些能力」，统计数字是第二位的。

### 3.4 实现上的注意

- 图表**不要引 CDN**：这是离线内网工具，`assets/webui/` 里现在一个外部依赖都没有。
  条形/柱状用 CSS + div 就够（现有 `.pbar` 已经是这个路子），真需要折线再手写 SVG。
- 聚合放 Python 端（`Api.usage_summary()`），前端只负责画。JS 里做几千行 JSONL 的
  聚合没必要，而且 Python 端还要给「周报推送」复用同一份聚合逻辑。

## 4. 还能展示什么（我的补充建议）

**值得做**

| 数据 | 为什么值得 |
|---|---|
| **一次做对率 / 返工率** | 比「省时间」更硬的价值。手工填错要返工，机器 94% 一次过，这个数字很有说服力 |
| **断点救回条数** | 「中途断了 N 次，自动续跑救回 M 条」——这是用户真实感受得到的痛点 |
| **最长的一次运行** | 「一次连续跑了 137 条 / 2 小时 41 分」，故事性强，适合放主页角落 |
| **抢会议室战绩** | 抢中率 + 最快抢到用时（毫秒级）。全工具最有画面感的一个数 |
| **单条平均耗时** | 每个配置类型一行 `平均每条 22 秒`。横向一比就知道哪个最费时间，也是优化的靶子 |
| **累计节约折算** | 「≈ 12 个工作日」「≈ 每周帮团队省 3.5 小时」。小时数太抽象，换算成人话才有感觉 |

**看情况**

- 版本分布（有多少人还在用老版本 → 该不该催更新）。维护角度有用，用户角度没意义，建议收进「稳定性」模块。
- 高峰时段热力图。好看，但对一个七种配置类型的内部工具来说信息量偏低。

**不建议**

- **人均排行榜置顶**。工具主页一旦变成 KPI 榜，用的人就开始琢磨数字而不是琢磨活。
- **把「节约金额」算出来**（工时 × 时薪）。看着唬人，但口径经不起推敲，一旦被质疑，
  连带前面所有真实数字一起失去可信度。

## 5. 已经能预见的坑

1. **重复计数**：同一批数据重跑、或者关掉重开再跑一遍，不能算两次节约。
   → `run_id` + `retry_of`，重跑只统计耗时不统计节约。
2. **空跑被当成战绩**：`dry_run` 模式一条没提交。→ 只计 `ok`。
3. **`state.json` 被清**：用户点「清除断点记录」后重跑，同一批数据会再次产生 `ok`。
   → 这个防不住，只能靠 `run_id` 去重同一份数据文件的重复提交，或者接受少量高估并在口径里注明。
4. **时区和时钟**：`meeting_api.py` 里已经在处理本机时钟偏差了。统计时间戳统一带时区写，
   聚合时按本地日切。
5. **文件越写越大**：一年下来几千行 JSONL，不大，但要有滚动策略（按月分文件，正好和
   §2.5 的 B 方案一人一月一文件对上）。
6. **统计不能挡业务**：写失败、盘不通、目录没权限，全部静默降级，只往 `run.log` 记一句。
7. **⚠ 静默降级 ≠ 静默丢数据**（2026-08-21 实测踩到）：有人用了一整天，团队表里一条没有。
   三个原因叠在一起 ——
   ① 上报只在「跑完一轮」之后触发，而它是个后台线程：人点完「跑完了」就叉掉窗口，
     十几秒的上报根本走不完；
   ② 上报失败（企微文档没登录 / 表格没加载完 / 浏览器没开）只写日志，界面上一个字都没有；
   ③ 只报「本周和上周」，所以失败超过两周的数据永远补不回来。
   → 现在的做法：本地存一份「上次成功写进表格的是什么」（`output/usage-reported.json`），
   **对不上就重写，欠多少周补多少周**；上报时机从「跑完一轮」扩到「跑完 + 启动时 +
   点了启动浏览器之后 + 手动点按钮」；首页显示「还有 N 周没上报」和失败原因。
   ⚠ 只有真写进去了才记账 —— 记早了就又回到静默丢数据的老路上。

## 9. 阶段 2：首页和数据统计分家之后的调整（2026-08-27）

「首页」只留一屏关键数字 + 功能导航，明细全部搬到侧栏的「数据统计」。这一页这次动了三处：

**① 去掉近 12 周柱状。** §7 ③ 当初的判断是「回答是越用越多还是三分钟热度」，
但实际用起来不成立 —— 这类工具本来就是攒一批集中跑，十二个格子里通常只有两三格
有数，剩下全是空档；一屏最显眼的位置上摆着一张几乎全空的图，读不出趋势，
只读得出「没什么人用」。数据还在（`usage.summarize` 的 `weeks` 照旧算），
只是不再画出来。

**② 新增「这些数字怎么来的」。** 顶部四宫格是四个结论，这一块补的是它们的分母：

- 左边一个环形图：条数落在**成功 / 失败 / 跳过**哪一边，中心是「一次做对」率。
- 右边两条对比条：**人工要花**（估）和**机器实跑**（实测），两条同尺归一，
  差额就是「省下工时」。

⚠ 两条对比条**不能叠成一条堆叠条**。`saved` 是逐次运行 `max(0, 人工 − 机器)`
累加出来的，机器比人工还慢的那几次贡献 0，所以「机器实跑 + 省下」并不恒等于
「人工要花」。叠成一条等于宣称它们相加，那是假的。

**③「用在哪儿了」一行改成两条。** 上条是条数（成功/失败分段），下条是省下的时间，
各按自己那一列的最大值归一。§7 ② 说的那个反差 ——「条数最多的和最费时间的通常不是
同一个」—— 原来只写在副标题里，没有图能对着看，现在两条一比就出来了。

实现上一个外部依赖都没加：条形是 div + 百分比宽度，环形是内联 SVG 的
`stroke-dasharray`。原因见 `assets/webui/style.css` 里那段注释 —— 离线内网工具，
而且 `assets/` 整个进那个 300KB 的代码包。
