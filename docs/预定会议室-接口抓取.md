抓取时间：2026-08-19
页面：<https://administration.biliapi.net/f1-space/web/index.html#/home/meeting/reserve>
所有路径都在 `https://administration.biliapi.net/f1-space` 下。

**这个配置类型不点 DOM，全走接口。** 原因见下面「为什么不点 DOM」。

## 1. 抢占窗口 —— 每天 10:00，按**工作日**算

### 规则原文

2026-08-20 往一个还没开放的日期提交预定，后端把规则原样吐了出来：

```
10点之前只能预定5个工作日之内的会议室，10点之后才可预定第6个工作日的会议室
```

也就是：**每天 10:00 放出一天**，而且数的是**工作日**，不是自然日。
今天算第 1 个工作日。

### ⚠ 第一版把这条写错了

第一版写的是「提前 7 个自然日，零点开放」。两处都错：

- **零点是猜的。** `GET /meeting/order/{roomId}/reservable/date` 返回的是一个零点
  时间戳，那只是说明「最远能订到**哪一天**」，压根没说这个值是在一天中的几点翻的。
  把「日期是零点」当成「零点翻页」，是没有证据的推断。
- **自然日只是碰巧对得上。** 从任意工作日往后数 6 个工作日，正好跨一个周末，
  等于 +7 个自然日 —— 所以在不遇节假日的平日里，7 天这个错模型看不出毛病。
  一撞上法定节假日或调休补班就整个偏掉。

### 验证

| 观测时刻 | `reservable/date` | 按「今天算第 1 个工作日」数 |
|---|---|---|
| 2026-08-19(周三) 下午 | 2026-08-26 | 三1 四2 五3 一4 二5 **三6** ✅ |
| 2026-08-20(周四) 下午 | 2026-08-27 | 四1 五2 一3 二4 三5 **四6** ✅ |

### 代码怎么处理

`meeting_data.open_moment(target)` 按上面这条规则算出「哪天 10:00 开抢」，
做法是从 target 往回走，走到「那天 10 点还够得着 target」的最早那天。

**但本地算不准工作日** —— 法定节假日和调休补班没有权威日历，硬编一份迟早过期。
所以本地算出来的时刻只用来决定「机器人哪天醒过来」；真正扣扳机前，
`MeetingRunner._wait_for_window()` 一定拿 `reservable/date` 跟服务端核一次：

- 本地负责「大概哪天该醒」
- 服务端负责「现在到底能不能订」

算早了无非多问几轮；节假日把窗口推后了也不会抢空。

另外，提交时如果窗口其实还没开，后端会回上面那句规则原文 ——
`MeetingRunner._is_not_open()` 认这个，认出来就退回去继续等，
**不能当成「这间房没了」去换下一个候选**，否则会在窗口打开前把候选一个个打空。

### 另有 canReserve

`POST /dd/meeting/check/canReserve` `{meetingRoomId, bookDate}` → `{canReserve, reason}`
查的是某间房某天有没有被行政「下线」（reason 是「会议室用途：晋升答辩 / 下线周期：…」），
**和预定窗口无关** —— 实测对窗口外的日期它照样返回 `canReserve: true`。别拿它判窗口。

## 2. 查询：某天所有会议室 + 占用情况

```
POST /meeting/order/spaces
{"conditions":[{"field":"bookDate","opt":"=","values":["2026-08-26"]}],
 "columns":[],"draw":2,"offset":0,"pageNumber":1,"pageSize":100}
```

返回每间房：

| 字段 | 说明 |
|---|---|
| `roomId` | 提交预定要用 |
| `roomName` | 形如 `206 为爱充电` |
| `capacity` | 可容纳人数 |
| `location` | 形如 `国正中心/2号楼/2F` |
| `resourceList` | `["白板","电视"]` |
| `needApprove` | 要不要审批 |
| `meetingCalendarResponseList` | **定长 48 的数组**，下标 i = `[i*30min, (i+1)*30min)`，`available` 是能不能订 |

半小时格下标换算：`14:00 → 28`、`14:30 → 29`。执行器里所有可用性判断都在下标空间做
（`meeting_data.slot_range`），不做字符串时间比较。

### conditions 支持的 field（从 `static/js/26.*.js` 的 query() 里读出来的）

`bookDate` / `bookTime` / `bookTimeLength` / `location` / `typeId` / `roomName` / `capacity` / `resourceIds`

实测结论：

- **`capacity` 好用，语义是「≥」**。传 12 会返回 14/16/18/24 的房。留着用，能少翻几页。
- **`location` 是坏的，别用**。前端传的是 `id + "-" + label` 里 split 出来的那个 id：
  - 传 `"5"`（2号楼的 id）→ 返回 0 条
  - 传 2号楼各楼层的 id → 也是 0 条
  - 传 `"6_5"` / `"GZ2"` / `"2号楼"` / `"5-2号楼"` → 后端直接 **500**，`data.message` 是
    `For input string: "GZ2"`（它在做 `Integer.parseInt`）
  - 传 `"1"` 倒是返回了国正中心的房，传 `"15"` 返回的是边城大厦 —— 层级对不上，明显是坏的

  所以**楼栋一律在客户端筛**：拿返回的 `location` 字段做子串匹配
  （`"国正中心/2号楼" in location`）。`config/forms/预定会议室.yaml` 的 `buildings`
  就是这么用的。

### ⚠ 窗口外返回 0 条

`bookDate` 超出可预定范围时 `data` 是空数组，**拿不到那天有哪些房**。

这直接决定了执行器的预热策略：会议室花名册（roomId / capacity / location）跟日期
无关，所以用**今天**查一次拿花名册、排好候选顺序，到点直接对第一名发预定，
省掉「查询 → 再提交」那一次往返（`MeetingRunner._warmup`）。

## 3. 提交预定

```
POST /meeting/order
{"roomId":20952, "start":"2026-08-19 22:00:00", "end":"2026-08-19 22:30:00",
 "subject":"会议主题", "content":"", "attendeeList":[], "reminderTime":2,
 "services":[], "remarks":"", "userId":32020, "attachments":[],
 "sign":"e42667d7d4aaa81308419f163b9db9b3"}
```

成功：`{"success":true,"message":"预定成功"}`

### ⚠⚠ 拒绝也返回 `success: true`

**这是这套接口最坑的一处，判错了后果最严重。**

2026-08-20 往一个还没开放的日期提交：

```json
{"success": true,
 "message": "10点之前只能预定5个工作日之内的会议室，10点之后才可预定第6个工作日的会议室"}
```

`success` 是 `true`，但「我的预定」里**查无此条** —— 根本没建出来。

照着 `success` 判的话，机器人会把「没抢到」记成「抢到了」：写进断点、不再重试、
在界面上报成功，人到点去开会才发现没房。

所以 `MeetingApi.reserve()` 改成 **message 里明确出现「成功」才算成功**，
其余一律当失败。成功时的原文是「预定成功」。

而且「窗口还没开」和「这间房被人抢走了」要分开：
`MeetingRunner._is_not_open()` 认前者 —— 认出来要**退回去继续等**，
不能当成「换下一个候选」，否则会在窗口打开前把候选一个个打空。

### ⚠ 「房被占」的原文还没抓到

`MeetingRunner.TAKEN_HINTS` 那串词（已被预定 / 不可预定 / 冲突 …）是**照着后台的
口气猜的**，这里从来没抓到过真实回话 —— 抓包那几次都没撞上「刚好被人抢先」。

猜漏了的后果不是崩，是**观感上的死循环**：认不出「被占」就会走「非正常失败」
分支，每次都在界面上打一条 warn，同样几个会议室名字反复滚。

所以 `_grab()` 现在把每种没见过的失败原文往 `run.log` 落一次
（`log.info("预定被拒：…")`，同一句只落一次，不刷屏）。**下次真撞上被抢先时，
去 run.log 把原文捞出来补进 TAKEN_HINTS，并回来补这一节。**

#### 已经抓到的一条：`空间异常，预定失败`

2026-08-24 真机跑出来的（`805 了解一下`，roomId=3614）。特征：

- `spaces` 明明把这间房报成**空闲**，`reserve` 却必然失败，反复试也是同一句；
- 所以它**不是**「被人抢走了」，不能进 `TAKEN_HINTS` —— 进了就变成
  「等等再来」，而它等到天亮也不会好。它属于「这间房就是订不了」，
  归 `_grab()` 里 `dead` 那一档：连着两次同样的回话就把这间房摘掉。

实测对比（同一条任务、同一间房）：

| | 改之前 | 改之后 |
|---|---|---|
| 40 秒内对 805 发了几次预定 | 7 次（真实 600 秒超时 ≈ 105 次） | 2 次 |
| 结论 | `空间异常，预定失败（试过 1 间，等了 40秒）` | `符合条件的 1 间全被服务端拒绝：空间异常，预定失败` |
| 何时结束 | 死等到 `grab_timeout_seconds` | 摘光候选就立刻结束 |

### ⚠ baseInfo 会偶发返回 404 网页

2026-08-24 11:31 实测：`GET /settings/emps/baseInfo` 返回了一整页
`<!DOCTYPE html>`（title 是「请求的网页不存在」），整轮抢占当场中断；
11:32 原样重跑就成功了。

判断是新开的标签页还没落地、或者 SPA 的 hash 路由还在跳，`fetch` 的相对路径
打到了没有 `/f1-space` 的落地页上。所以 `MeetingApi.me()` 现在会**等页面落定后
重试一次**，第二次还失败才抛。

⚠ 恢复动作只能是 `ensure_page()`，**不能无条件 `goto(PAGE_URL)`**。
2026-08-24 实测：页面本来好好地停在行政平台上，硬 goto 一次会触发一轮 SSO 弹跳
（落到 `http://…/f1-space/oauth/callback?code=…`），有几率把标签页直接打成
`chrome-error://chromewebdata/` —— 比原来那个瞬时失败严重得多。
`ensure_page()` 只在页面**不**在行政平台上时才导航，在的话只等它安静下来。

顺带：`_call` 兜底会把响应体的前 500 字符塞进 `body.raw`，是网页的话这 500 个
字符会原样进日志（当时 run.log 里就是一整段 CSS）。`meeting_api.html_error()`
负责把它折成一句人话。

### ⚠ SSO 之后页面会落在 http，认标签页不能带 scheme

2026-08-24 实测：登录态过期后走一遍 SSO，页面最终稳定在

```
http://administration.bilibili.co/f1-space/web/index.html#/home/meeting/reserve
```

**是 `http://`，不是 `https://`**。而且这个明文 origin 上 `fetch` 照样带得上
cookie，`me()`／`spaces()` 全都正常。

所以 `is_admin_url()` 按**域名**认，不按 scheme 认。只认 https 的后果不是报错，
是更隐蔽的东西：`MeetingRunner._pick_page()` 认不出这个已经开着的标签页，于是
每跑一次新开一个；而新开的那个 goto 之后同样落在 http，**永远不会被复用** ——
这东西要挂着跑几天，标签页会一次次堆积。（真机验证过：旧代码 1 个标签页跑一次
变 2 个，新代码保持 1 个。）

⚠ 匹配的是 host 全等，不是 `startswith` —— `administration.bilibili.co.evil.com`
这种要挡掉。

### ⚠ sign 签名

```
sign = md5(roomId + start + end + reminderTime + userId)   // JS 字符串直接拼接，md5 hex
```

从 `static/js/26.*.js` 的 `createMeeting()` 里逆出来的：

```js
var n=(0,c.default)(e.roomId+e.start+e.end+e.reminderTime+e.userId);
$.ajax({url:"/meeting/order",type:"POST",data:JSON.stringify(p(p({},e),{},{sign:n})),...})
```

`c.default` 是 js-md5（同一个包里能搜到 `crypto.createHash("md5")…digest("hex")` 的
node 分支），就是普通 md5 十六进制。

**验证过**：2026-08-19 用 `20952 / 2026-08-19 22:00:00 / 2026-08-19 22:30:00 / 2 / 32020`
真实提交了一次，返回「预定成功」，随后取消。Python 侧 `hashlib.md5` 算出来一模一样。

拼接顺序和每个值的字符串形态都不能动：数字直接转十进制字符串，start/end 是
`YYYY-MM-DD HH:mm:00`（秒必须是 00）。

### start / end 的形态

前端 `getMeetingTime()` 的逻辑：点一个格子 → start = 该格起点，end = 该格起点 + 30min，
秒一律抹成 `00`。**结束时间正好落在次日 00:00 时要写成当天 `23:59:00`**
（前端是 `+30min` 之后再 `-1min`），写 `24:00:00` 或滚到第二天后台都不认。
见 `meeting_data.submit_times()`。

### reminderTime

`0` 不提醒 / `1` 准时 / `2` 提前15分钟（页面默认）/ `3` 提前30分钟 /
`4` 提前1小时 / `5` 提前2小时 / `6` 提前1天

## 7. 为什么不点 DOM

这是**抢占**场景，不是填表。窗口开的那一瞬间全公司都在刷：

- 点 DOM：等 SPA 把日历渲染出来（318 间 × 48 格）→ 定位到具体格子 → 开表单 →
  填主题 → 点预定。实测是「秒」级。
- 发接口：一个 POST。「百毫秒」级。

差的这一个数量级就是抢得到和抢不到的区别。

请求全部在用户那个已登录页面的 origin 里用 `fetch` 发（`page.evaluate`），
Python 侧不自己带 cookie —— 和这个项目其它执行器一样，脚本永远不碰账号密码。

⚠ 坑一：**两个域名**。`administration.biliapi.net` 会跳到 `administration.bilibili.co`
（2026-08-20 实测）。只认一个的话，已经开着的行政平台标签页会认不出来，
于是去征用用户正在看的别的页；而且每次 `ensure_page` 都觉得「不在目标域名上」，
白导航一遍。见 `meeting_api.ORIGINS` / `is_admin_url()`。

⚠ 坑二：`Browser` 拿的是 `contexts[0].pages[0]`，也就是最早开的那个标签页。
直接用它会把用户正在看的别的后台页面导航走（实测顶掉过广告后台的单元页）。
`MeetingRunner._pick_page()` 先找已经开在行政平台上的标签页，
一个都没有就**新开一个**，绝不征用当前页。新开的跑完不关 —— 下次跑会认出来复用，
不会越积越多。

⚠ 另一个坑：这套 SPA 落地后自己还会再跳一次（hash 路由初始化），紧接着发 evaluate
会撞上 `Execution context was destroyed`。`MeetingApi.ensure_page()` 多等一个
networkidle，`_call()` 遇到这个错重发一次。

## 8. 时钟

抢占掐的是 10:00:00 整点，本机时钟偏几秒就可能整轮扑空。`MeetingApi.clock_skew()`
用响应头的 `Date` 测「服务器时间 − 本机时间」，取几次中位数。
实测这台机器快 1.0~1.2 秒。执行器全程用 `_now()`（已校准）而不是裸 `datetime.now()`。

`Date` 头只到秒，单次采样最大 1 秒误差，所以另外还有 `grab.preroll_ms` 的提前量兜底。
