## 只有三处不一样

### 1. 类型下拉的默认值和文案

| | 花火内容授权 | 普通内容授权 |
|---|---|---|
| 字段 label | 视频 | **稿件** |
| 类型下拉默认 | 视频链接 | **稿件链接** |
| 选项全集 | 视频链接 / 稿件avid / 稿件bvid | 稿件链接 / 稿件avid / 稿件bvid |

一样要每次切成「稿件bvid」。输入框 placeholder 两边都是「请输入需要绑定的bilibili视频」。

### 2. 校验接口（预检就靠它）

```
GET /platform/api/web_api/v6/resource/sanlian/general_video/authorize/state?archive_id=BV1Nibn63EPm
```

```jsonc
// 能在这一页授权
{"status":"success","result":{"auth_times":0,"renewal_times":0,"has_authorized":false,
 "archive_info":{"title":"...","bvid":"...","avid":"...","mid":"3493288858356086","nick_name":"181319","cover":"...","face":"..."}}}
// 花火商单稿件（要去隔壁）
{"status":"fail","error_msg":"获取视频授权状态失败：该稿件是商单稿件，请到花火平台进行绑定"}
```

⚠ **和花火那个接口正好互补**：2026-09-23 实测同一份 38 条清单，
这里 36 条 success、2 条是商单稿件；拿去花火那页跑正好反过来。
**一条稿件只会在其中一页能授权**，所以两个配置类型是「二选一」，不是「先后跑两遍」。

比花火那个多回两样有用的：`has_authorized`（已经授权过了，别重复申请）、
`archive_info.mid` / `nick_name`（UP 主，配额归并要用）。

### 3. ⚠ 3 次/7 天的上限算在「同一账号」，不是「同一视频」

弹窗顶部的 alert 原话：「发送申请绑定后，请UP主到bilibili消息列表进行确认操作;
**7日内对同一账号仅有3次申请机会**，已使用（0/3）次。」
（花火那边是「7日内对同一**视频**仅有3次申请机会」。）

这条决定了预检要多做一步：**按 `mid` 把清单归并，同一个 UP 主超过 3 条的部分标红拦下**
（`src/nc_runner.py` 的 `_apply_quota`，上限写在 yaml 的 `quota:` 段）。
清单是按视频排的，人眼很难看出「这 5 条是同一个 UP 主」，不拦的话后面几条发出去必被拒。

确认路径也不同：这里是 **UP 主到 bilibili 消息列表**确认，花火那边是去花火平台商单详情页。
